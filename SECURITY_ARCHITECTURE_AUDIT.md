# Аудит безопасности и приватности NeyLivo

Дата: 2026-08-12. Версия кода: 1.556.1 (коммит `70a7a55`).

Это разбор того, что происходит на самом деле, а не того, что хочется написать на
сайте. Каждое утверждение здесь указывает на файл и строку или на живую проверку,
которую можно повторить. Всё, что не подтверждено кодом, помечено как
предположение.

Порядок: сначала находки по важности, потом разбор по слоям, потом план
исправлений.

---

## Кратко

Что сделано хорошо:

- Правила доступа к таблицам (RLS) написаны подробно и проверяются настоящим
  Postgres — `scripts/db-test/rls-test.mjs`, 1516 строк, включая нарочные поломки.
- Чтение таблиц без входа закрыто (миграция `76_read_requires_login.sql`),
  проверено живым запросом: аноним получает пустой список.
- Сквозное шифрование личных сообщений — настоящее (ECDH P-256 + HKDF-SHA256 +
  AES-256-GCM), с отпечатками для сверки и без тихого отката к открытому тексту.
- Плагины изолированы браузером, а не проверками: Web Worker, а страницы плагинов —
  `<iframe sandbox="allow-scripts">` без `allow-same-origin`, то есть чужое
  происхождение.
- Ни аналитики, ни сборщика падений, ни рекламных счётчиков в коде нет вовсе.

## F1. Вложения лежат в публичном хранилище и перечисляются кем угодно

**Важность: высокая. Это главная находка аудита.**

### Что в коде

`supabase/04_storage.sql`:

```sql
create policy "attach_read" on storage.objects for select using ( bucket_id = 'attachments' );
create policy "avatars_read" on storage.objects for select using ( bucket_id = 'avatars' );
```

У правила нет `to authenticated`. Значит оно совпадает и для роли `anon` —
той самой, чей ключ лежит в собранном веб-приложении и виден любому, кто откроет
исходник страницы. То же у `modfiles` (`44_modfiles_storage.sql`).

Путь объекта задаётся в `src/lib/storage.ts:37`:

```
<bucket>/<uid>/<время в миллисекундах>_<имя файла>
```

Имя файла настоящее, только с заменой небуквенных символов. То есть даже имя
объекта — уже содержание: `2024_договор_аренды.pdf`, `справка.jpg`.

### Что проверено вживую

Проверено на рабочем проекте, обычными запросами к хранилищу:

1. **Перечисление работает** — с публичным ключом, который и так лежит в сборке
   веб-приложения, отдаётся список папок бакета. Папки — это идентификаторы
   пользователей, внутри каждой файлы этого человека с настоящими именами.
2. **Скачивание работает вообще без ключа** — публичный адрес объекта отдаёт
   содержимое без входа и без какого-либо заголовка.

То есть любой человек в интернете может выгрузить вложения всех пользователей: и
отправленные в личной переписке, и в каналах, и аватарки.

Точная последовательность запросов здесь не приводится намеренно — она есть у
владельца проекта. Всё, что нужно для исправления, ниже; всё, что нужно для
злоупотребления, — нет.

### Что не затронуто

- Файлы, отправленные при включённом «шифровать вложения»
  (`settings.e2eeFiles`, по умолчанию выключено): они лежат зашифрованными
  AES-256-GCM, под именем `enc`, с типом `application/octet-stream`
  (`src/lib/crypto/files.ts`, `src/components/DMHome.tsx:1173`). Такой файл
  скачать можно, прочитать — нет.
- Таблицы. Сообщения, профили, серверы для анонима закрыты — проверено запросом,
  ответ пустой.

### Почему это важнее, чем кажется

Приложение позиционируется как приватное и шифрует текст личных сообщений. Но
отправленная в той же переписке фотография до сих пор лежит открыто, если человек
не нашёл переключатель в настройках. Получается защита, в которую человек верит
больше, чем она есть.

### План исправления без потери файлов

Менять архитектуру вслепую нельзя: у `getPublicUrl` нет срока годности, и ссылки
на вложения зашиты в тысячи старых сообщений (`messages.attach_url`). Если просто
сделать бакет приватным, все старые картинки в переписке превратятся в битые.

Порядок, при котором ничего не пропадает:

1. **Сначала закрыть перечисление.** Это одна строка и ломает только возможность
   выгрузить всё разом:
   ```sql
   drop policy if exists "attach_read" on storage.objects;
   create policy "attach_read" on storage.objects for select to authenticated
     using ( bucket_id = 'attachments' );
   ```
   После этого нужен хотя бы вход в приложение, чтобы перечислить бакет. Прямые
   публичные ссылки продолжают работать — старые сообщения не ломаются.
2. **Перевести отдачу на подписанные ссылки.** В `src/lib/storage.ts` заменить
   `getPublicUrl` на `createSignedUrl` с коротким сроком, а в местах показа
   (`FileCard`, `Lightbox`, `BigAttachment`) научиться обновлять просроченную
   ссылку. Хранить в базе не готовый URL, а путь объекта.
3. **Перевести старые записи.** Разовый скрипт: `attach_url` вида
   `.../object/public/attachments/X` → путь `X`. Файлы не двигаются вовсе,
   меняется только текст ссылки в базе.
4. **Выключить публичность бакета** (`update storage.buckets set public=false`).
   Делать только после шага 3, иначе старые сообщения осыпятся.
5. **Включить шифрование вложений по умолчанию** для личной переписки. Это
   единственный шаг, после которого хранилище перестаёт быть доверенным звеном
   вовсе, а не просто закрывается на ключ.

Шаг 1 стоит сделать немедленно и отдельно от остальных: он ничего не ломает.

## F2. Шифрование выключено по умолчанию и покрывает не всё

`src/lib/settingsStore.ts:152`:

```ts
e2ee: false, e2eeCalls: false, e2eeFiles: false
```

Все три переключателя выключены у нового человека. Где применяется —
`src/components/DMHome.tsx:1186`:

```ts
if (settings.e2ee && active && !activeGroup && (t || fileKeys.length))
```

Отсюда следует точная граница:

| Что | Шифрование от устройства до устройства |
|-----|----------------------------------------|
| Личная переписка один-на-один | Есть, по желанию, по умолчанию выключено |
| Вложения в такой переписке | Есть, отдельным переключателем, по умолчанию выключено |
| Звонок один-на-один | Есть, отдельным переключателем, по умолчанию выключено |
| Групповая личная переписка | Нет |
| Каналы серверов | Нет |
| Голосовые каналы серверов | Нет |

Это не изъян реализации, а честная граница возможностей: групповое шифрование —
отдельная и большая задача (см. `E2EE_DESIGN.md`).

Что сделано правильно: **тихого отката к открытому тексту нет**
(`src/lib/crypto/dm.ts`). Если зашифровать не для кого, сообщение не уходит
вовсе, и человек видит причину. Это важнее самой криптографии: молчаливый откат
превращает защиту в её видимость.

Одно исключение: **звонок при неудаче шифрования идёт незашифрованным**
(`DMHome.tsx:451`), с уведомлением на экране. Решение объяснено в коде
(оборвать звонок хуже), но на странице безопасности это должно быть написано, а
не спрятано.

### Что означает «нет сквозного шифрования» для канала сервера

Сообщения каналов лежат в базе открытым текстом. Их не видит посторонний (RLS), но
их видит тот, у кого есть доступ к базе, то есть владелец проекта Supabase. Так
устроены Discord, Telegram (обычные чаты) и Slack; писать «сервер не может
прочитать ваши сообщения» про каналы NeyLivo нельзя.

## F3. Резервная копия ключа заперта паролем, который проходит через сервер

`src/lib/crypto/backup.ts`: приватный ключ устройства выгружается в JWK,
запирается ключом из пароля (PBKDF2-SHA256, 250 000 повторов, соль 16 байт,
AES-256-GCM) и кладётся в таблицу `key_backups`. Параметры выбраны разумно,
пароль на сервер не отправляется — запертое уезжает уже запертым.

Но тот же пароль человек вводит на экране входа, и оттуда он уходит в Supabase
Auth в открытом виде (иначе проверить его нельзя — так работает любая система с
паролем). Значит:

> Тот, кто управляет сервером аутентификации, может при очередном входе человека
> перехватить пароль, взять из базы его `key_backups.wrapped` и получить ключ от
> личной переписки.

Это ровно то, что в коде названо ценой решения (`core.ts:34`): без копии человек
терял всю переписку при каждом выходе из аккаунта. Но в модель угроз это входит и
должно быть написано на странице безопасности прямым текстом: **NeyLivo защищает
переписку от постороннего и от утечки базы, но не от недобросовестного владельца
самого сервера.**

Способ убрать это ограничение — отдельный пароль для копии ключа, который нигде,
кроме шифрования копии, не используется. Задача небольшая и стоит того.

## F4. Нет Content-Security-Policy

`index.html` — никакого `<meta http-equiv="Content-Security-Policy">`.
В Electron (`electron/main.cjs`) заголовок ответа тоже не ставится.

Насколько это опасно сейчас: умеренно. Разметка сообщений рендерится React-узлами,
`dangerouslySetInnerHTML` в коде нет ни одного (проверено поиском по всему `src`),
`hl.tsx` прямо об этом пишет. То есть очевидного пути для внедрения кода не видно.
CSP тут — второй рубеж, который ловит ошибку, которую однажды сделают.

Что мешает включить прямо сейчас: страницы плагинов используют `srcdoc` и
подгружают библиотеки со сторонних адресов, музыка встраивает проигрыватель
YouTube, эмодзи грузятся с jsDelivr. Политику придётся писать не «одной строкой»,
а с разбором каждого источника. Предложение — начать с `frame-ancestors 'none'`,
`object-src 'none'`, `base-uri 'self'`: они ничего не ломают и закрывают часть
путей.

## F5. Окно Electron не защищено от ухода на чужой адрес

`electron/main.cjs:1560` — `setWindowOpenHandler` есть, внешние ссылки уходят в
системный браузер. А обработчика `will-navigate` нет: если внутри страницы что-то
уведёт документ на чужой адрес, он откроется прямо в окне приложения, где рядом
живёт `preload.cjs` со своими каналами.

Настройки самого окна при этом правильные: `contextIsolation: true`,
`nodeIntegration: false`, у вспомогательных окон явный `sandbox: true`.

Исправление — четыре строки: на `will-navigate` отменять всё, кроме своего
`file://`/`localhost`, и отдавать в `shell.openExternal`.

## F6. Плагин без строки `@permissions` получает все разрешения

`src/lib/plugins/manifest.ts:57`: «НЕ НАПИСАЛ `@permissions` — значит ВСЕ».
То же делает `*` (осознанно, с красным предупреждением на экране установки).

Само по себе решение владельца, и человеку всё показывают перед установкой. Но
«забыл написать» и «сознательно попросил всё» выглядят для человека одинаково, а
означают разное. Стоит хотя бы отличать их на экране установки словами.

### Что при этом сделано по-настоящему

Изоляция не декларативная, её обеспечивает браузер:

- код плагина — в `Worker` из blob-URL (`src/lib/plugins/sandbox.ts`), без DOM,
  без `localStorage`, без сессии;
- страницы плагинов — `<iframe sandbox="allow-scripts">` **без**
  `allow-same-origin` (`src/lib/plugins/htmlFrame.ts:23`), то есть уникальное
  чужое происхождение: ни документа приложения, ни его хранилища;
- сеть — один проверяющий на все способы выхода (`netGuard.ts`): только `https`
  и `wss`, только домены из `@hosts`, никогда к самому NeyLivo и его серверу,
  заголовки по белому списку, `Cookie` запрещён всегда;
- каждый вызов сверяется с разрешениями в одном диспетчере (`api.ts`), а не в
  двух местах.

Есть отдельная проверка на попытки обхода — `npm run test:attack`.

Чего нет: **никаких пределов на количество** (частота сообщений, запросов, число
окон, размер данных). Убрано осознанно в v1.489.0 по указанию владельца, осталась
только защита самого приложения от зависшего плагина — сроки ожидания
(`limits.ts`). Установленный плагин действует от имени человека без ограничений,
и приложение говорит это прямым текстом перед установкой.

## F7. Сторонние сервисы

Ни аналитики, ни сборщика падений, ни рекламы в коде нет
(проверено поиском по `posthog|sentry|gtag|google-analytics|mixpanel|amplitude|telemetry`
— единственное совпадение это комментарий «своего Sentry нет»). Ошибки пишутся в
`localStorage` и никуда не уходят.

Но запросы к чужим адресам есть, и каждый такой запрос отдаёт IP-адрес человека:

| Сервис | Зачем | Когда |
|--------|-------|-------|
| Supabase | база, вход, хранилище, реальное время | всегда |
| LiveKit | голос, видео, демонстрация экрана | во время звонка |
| jsDelivr (Twemoji) | картинки эмодзи | **всегда, без действия человека** |
| Tenor (Google) | поиск GIF | при открытии GIF-панели |
| lrclib.net | тексты песен | при запросе текста |
| Audius, SoundCloud (noembed), YouTube | музыка по ссылке | при добавлении/игре трека |
| Deezer, iTunes | обложки и метаданные | при поиске трека |
| SteamGridDB | обложки игр | при показе активности с игрой |
| OpenDota | статистика Dota 2 | по запросу в профиле |
| Hugging Face | скачивание модели распознавания | только по нажатию |
| Render | аварийный чат | только когда Supabase недоступен |

Выделю `jsDelivr`: он получает запросы у каждого человека сразу после запуска,
без единого действия, просто потому что в интерфейсе есть эмодзи. Это самый
незаметный из перечисленных и самый лёгкий для устранения — набор Twemoji можно
положить в сборку.

## F8. Пароль от шести символов

`src/auth/AuthScreen.tsx:41` разбирает ответ сервера «password should be at least»
— это порог Supabase по умолчанию, шесть символов. Своей проверки в приложении нет.

Хранением паролей занимается Supabase Auth (bcrypt), своего кода хранения в
проекте нет — и это правильно.

Стоит поднять порог до восьми в настройках проекта и добавить понятную подсказку
в форме, а не только разбор чужой ошибки.

## Разбор по слоям

### Вход и учётные записи

- Регистрация по почте и паролю через Supabase Auth. Вход — по почте или по
  юзернейму (`supabase/functions/login-by-username`, ответ на неверный логин и
  неверный пароль одинаковый — перебрать список имён нельзя).
- Сессия (JWT + токен обновления) хранится в `localStorage`, на Android
  дублируется в нативное хранилище (`src/lib/authStore.ts`). Для веба это
  обычная практика; означает, что код, выполняющийся на странице, до неё
  добрался бы — но плагинам страница недоступна (см. F6).
- Доверенные устройства и код восстановления (`108_device_guard.sql`): хранится
  только SHA-256 отпечаток кода, не сам код. Сделано верно.
- Вход по QR (`109_qr_login.sql`, `src/lib/qrLogin.ts`).
- Удаление аккаунта в приложении есть (`DeleteAccountModal.tsx`, `src/lib/wipe.ts`).

### Сообщения и правила доступа

- 110 миграций, RLS включён на всех таблицах. Ранние правила были широкими
  (`schema.sql`: `messages_read using (true)`), но позже сужены:
  `54_security_hardening`, `69_channel_privacy`, `71`, `72_harden_permission_functions`,
  `76_read_requires_login`, `85`/`87_perm_fixes`, `101_security_fixes`.
- Проверка правил — настоящая: `npm run test:db` поднимает Postgres (pglite),
  применяет все миграции по порядку и играет за нескольких пользователей.
- Живая проверка: аноним с публичным ключом получает по `messages` и `profiles`
  пустой список.

### Звонки

LiveKit. Токен выдаёт Edge Function `livekit-token`, и она же решает, можно ли
звонить: проверяет блокировку и настройку «кто может звонить» (`all` / `friends` /
`favorites` / `none`) сервисным ключом, не полагаясь на клиента. Сделано верно.

Без включённого шифрования звонка медиапоток расшифровывается на сервере LiveKit —
как в любом обычном групповом звонке.

### Edge Functions

Смотрел `livekit-token`, `login-by-username`, `send-push`, `bot-api`, `webhook`.
Заметно, что права проверяются руками сервисным ключом там, где RLS не работает
(у ботов нет сессии), и что это делалось не с первого раза, а по следам разбора:
в `send-push` подробно описано, как раньше любой вошедший мог отправить любому
человеку поддельное системное уведомление, и как это закрыли. Сейчас проверки на
месте.

`Access-Control-Allow-Origin: *` во всех функциях — приемлемо: доступ решает
токен в заголовке, а не источник запроса.

### Electron

`contextIsolation: true`, `nodeIntegration: false` у всех окон, у вспомогательных
явный `sandbox: true`, внешние ссылки уходят в системный браузер. Разрешения
(микрофон, камера, захват экрана, уведомления) выдаются без запроса
(`setPermissionRequestHandler`) — для своего приложения это осознанно, но значит,
что любой код на странице получил бы камеру без вопроса.

Не хватает: `will-navigate` (F5) и CSP (F4).

Обновление приложения — `electron-updater` с GitHub Releases, по HTTPS, с проверкой
контрольной суммы (sha512 из `latest.yml`). Именно контрольной суммы, а не
подписи: она подтверждает, что файл скачался целиком и не подменён по дороге, но
не подтверждает, кто его выпустил. Установщик неподписанный (нет сертификата) — Windows
SmartScreen будет предупреждать; это стоит честно объяснить на странице скачивания,
а не советовать людям отключать защиту.

### Android

`AndroidManifest.xml`: `allowBackup="false"` (правильно — сессия не уедет в
облачную резервную копию), `usesCleartextTraffic` не включён, наружу выставлена
только главная activity. APK подписывается настоящим ключом из секретов, и сборка
**падает**, если ключа нет (`release.yml`) — вместо тихой подписи одноразовым
отладочным ключом. Это хорошее решение: молча выпущенный APK, который никому не
установится поверх старого, хуже упавшей сборки.

## Что противоречит позиционированию «privacy-first»

По убыванию:

1. **F1** — вложения открыты всему интернету. Это прямое противоречие, и его надо
   закрывать первым.
2. **F2** — шифрование выключено по умолчанию. Приватность по умолчанию — это то,
   чем такой мессенджер отличается от обычного; сейчас человек получает защиту,
   только если сам её найдёт.
3. **F7 (jsDelivr)** — сторонний CDN узнаёт IP каждого пользователя без всякого
   его действия.
4. **F3** — модель угроз не покрывает владельца сервера, и это должно быть
   написано, а не подразумеваться.

## Что нельзя писать на сайте

- «End-to-end encrypted messenger» без оговорок — шифрование выключено по
  умолчанию и есть только в переписке один-на-один.
- «Сервер не может прочитать ваши сообщения» — про каналы серверов и групповые
  личные это неправда.
- «Анонимный» — для регистрации нужна почта, у сообщений есть автор, у сервера
  есть журнал действий.
- «Файлы защищены» — пока не сделан F1.
- Что угодно про аудит, сертификацию, число пользователей, сообществ и оценки.

## Что написать можно и нужно

- Сквозное шифрование личной переписки один-на-один: ECDH P-256, HKDF-SHA256,
  AES-256-GCM, ключ у устройства, отпечаток для сверки голосом, длина сообщения
  скрыта дополнением, без тихого отката к открытому тексту. С прямым указанием,
  что это переключатель, а не поведение по умолчанию.
- Плагины: Web Worker и чужое происхождение у страниц, 23 разрешения с понятными
  подписями, сеть по белому списку доменов, проверка на попытки обхода в наборе
  тестов.
- Ни аналитики, ни сборщика падений, ни рекламных счётчиков.
- Открытый исходный код: всё вышеперечисленное можно проверить.
